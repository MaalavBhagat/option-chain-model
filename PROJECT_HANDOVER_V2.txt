2. THE STRATEGY
================================================================================

An intraday short strangle on the NIFTY 50 index, sold at market open on
the weekly options EXPIRY day, closed before that same day's close --
never held overnight.

Entry rule (unchanged since pre-registration, commit 902da2c):
  - Call strike: nearest available strike >= index_open x 1.005 (0.5% OTM)
  - Put strike: nearest available strike <= index_open x 0.995 (0.5% OTM)
  - Sell both at that day's OpnPric. Buy both back at that day's ClsPric.
  - Volume filter: both legs must have TtlTradgVol > 1000 contracts, else
    the date is skipped and the reason logged (never silently dropped).

Expiry weekday regime change: NIFTY's weekly expiry moved from THURSDAY to
TUESDAY, effective 2025-09-02. This is established from THIS PROJECT'S OWN
DATA: same-day-expiry NIFTY rows in the downloaded bhavcopy files shift from
Thursday to Tuesday starting with the 2025-09-02 expiry (see
journal/2026-08-12-findings.md). NO NSE CIRCULAR HAS BEEN LOCATED OR CITED
anywhere in this project confirming the change or its effective date --
earlier project documents described this as "confirmed via real circulars,"
which overstated what had actually been checked; that phrasing was wrong and
has been corrected here. Treat 2025-09-02 as data-derived and correct as far
as this project's own bhavcopy history goes, but not independently verified
against a primary regulatory source (open question -- see the "Open
questions -- claims to verify" and "Claims verified from data vs claims
taken from secondary sources" sections near the end of this file). The
pipeline is regime-aware: Thursday before that date, Tuesday from it.
Holidays shift the actual expiry to the previous trading day -- this is
handled where the market is fully closed (HTTP 404 on download), but NOT for
the case below.

THE MONDAY 2025-10-20 EXCEPTION (important, read this):

  VERIFIED FROM DATA: the 2025-10-21 bhavcopy file exists and downloads
  successfully (HTTP 200, not 404). Directly checked against the raw file --
  it contains ZERO rows where TckrSymb=NIFTY and XpryDt=2025-10-21 (no
  genuine same-day-expiry NIFTY contract that day). The 2025-10-20 bhavcopy,
  by contrast, contains 186 such rows. The genuine weekly expiry that week
  was Monday 2025-10-20, not the expected Tuesday. The original downloader's
  holiday-rollback logic (which only triggers on a 404) never looked at
  Monday, because the market was nominally open on the 21st -- this part is
  confirmed directly from this project's own downloaded files, not asserted.

  NOT VERIFIED: the explanation for WHY 2025-10-21 has a real, downloadable
  bhavcopy with zero genuine expiries -- that 21 October 2025 was an
  official NSE trading holiday for Diwali Laxmi Pujan, on which NSE ran a
  ceremonial one-hour "Muhurat Trading" session -- is a plausible hypothesis
  consistent with well-known NSE/BSE conventions around Diwali, but it came
  from general/secondary knowledge, NOT a cited primary source. No NSE
  holiday calendar or circular is cited anywhere in this project confirming
  this specific date's holiday status or the Muhurat session. Treat this
  explanation as an unverified hypothesis, not a confirmed fact (open
  question -- see below).

  This gap was found by accident, months into the project, via an unrelated
  every-day-download experiment, and is now fixed IN THE DATA (the baseline
  is 137 trades, not 136) but NOT in the downloader's logic itself -- that
  limitation is documented, not patched (see section 4 and
  journal/2026-08-16-missing-expiry-day.md). If you extend the date range
  covered by this project, budget time to manually check for more cases like
  this one; the holiday-rollback logic as written cannot catch them.

12. THE EVERY-DAY EXTENSION, PHASE A+B (commits 2a93f8a, 060e104, 1eda0c9,
    2d5d657; journal/2026-08-16-everyday-*.md)
    Pre-registered test: does trading the same entry rule on EVERY day
    (not just expiry days) produce more profit? Two variants:
    nearest_weekly (DTE varies 0-6) and fixed_dte (~5 DTE target).
    STRUCTURAL WARNING, repeated in every output file: DTE>0 trades do
    NOT expire that afternoon, so closing price retains real time value
    -- never pooled with the expiry-day baseline or across DTE buckets.
    RAW RESULT: 4 of 5 pre-registered predictions FAILED (not softened):
      (a) mean P&L declines with DTE -- FAILED (not monotonic)
      (b) win rate falls with DTE -- FAILED (not monotonic)
      (c) stddev rises with DTE -- FAILED (DTE=2's stddev highest,
          driven by one outlier: 2024-06-04, independently recovered
          here in the every-day data as DTE=2's worst trade)
      (d) mean P&L after costs negative for DTE>=3 -- FAILED (stays
          positive through DTE=6)
      (e) DTE=0 subset reproduces the 137-trade baseline exactly -- HELD
    DTE=5 appeared to beat DTE=0 (24.02 vs 19.51 points/trade) --
    apparently contradicting the starting hypothesis's expected direction.
    THE CONFOUND CHECK (outputs/dte_confound_check.txt, commit 2d5d657):
    DTE buckets are largely proxies for weekday+regime, not time-to-
    expiry. DTE=2 is 100% pre-regime/95.4% Tuesday; DTE=3 is 95.1% pre-
    regime/95.1% Monday; DTE=4 is 97.9% post-regime/93.6% Friday. Holding
    period constant, DTE=0 restricted to post-2025-09-02 alone averages
    25.25 points -- HIGHER than DTE=5's 24.02. The DTE=5 advantage does
    NOT survive controlling for period; it was a recent-period effect.
    The clean comparison (fixed_dte vs nearest_weekly-DTE=0 on the SAME
    137 dates) DOES support prediction (a): DTE=0 (19.51 pts) beats the
    longer-dated leg (15.67 pts) -- though on these specific dates,
    fixed_dte's realized DTE skews to 7, not 5 (mathematically correct:
    on an expiry day, next week's DTE=7 is closer to the 5-day target
    than today's DTE=0), a design wrinkle worth remembering if you reuse
    this comparison methodology elsewhere.
    PLAIN CONCLUSION: the starting hypothesis "more trading days means
    more profit" is NOT supported once the confound is controlled for.
    Expiry-day-only trading outperforms per trade. This is documented in
    RESULTS_EXTENSIONS.md's "Every-day extension and the DTE confound"
    section.
    PIPELINE VALIDATION EVIDENCE: 2024-06-04's P&L was computed twice, by
    two independent scripts on two independent code paths, and agrees
    exactly: outputs/event_day_summary_stats.txt (src/event_day_study.py)
    records "2024-06-04  25  2  -5.59%  -19,415.00  -776.60 ..."; and
    outputs/everyday_results.csv (src/everyday_backtest.py) records the
    same date, DTE=2, "-776.6000000000001,25,bhavcopy,-19415.00..." in
    BOTH the nearest_weekly and fixed_dte variant rows. Same points
    figure (-776.60), same lot size (25), same rupee figure (-19,415.00),
    found by two unrelated pipelines built for two different studies.
    This is corroborating evidence the P&L engine is computing consistent
    results across independent code paths, not proof of correctness on
    its own.

5. WHY POINTS IS THE PRIMARY METRIC, AND THE LOT-SIZE STORY
================================================================================

NIFTY's lot size (contracts per lot) changed FOUR times across this
project's 2024-2026 data window, not once and not the three times a
citation I was given claimed. Confirmed directly from NewBrdLotQty, a
real per-contract field present in every NSE bhavcopy file (authoritative
-- checked and preferred over any inferred date):

  Lot size 50: 2024-01-04 (start of this project's data) to 2024-04-25
  Lot size 25: 2024-04-26 to 2024-11-19 (policy), individual contracts
               grandfathered through 2025-01-30
  Lot size 75: 2024-11-20 to 2025-10-27 (policy), individual contracts
               from as early as 2025-01-02
  Lot size 65: 2025-10-28 onward (policy), fully in effect 2026-01-06+

Real NSE circulars: FAOP61415 (50->25), FAOP64625 (25->75), FAOP70616
(75->65). Full detail: journal/2026-08-16-lot-size-audit.md.

WHY THIS MATTERS: NSE grandfathers an already-listed contract at its
ORIGINAL lot size until that specific contract's own expiry, rather than
switching everything on one calendar date. Since weekly contracts are
listed months ahead, two different lot sizes can genuinely coexist across
different expiries on the SAME trade date. Confirmed concretely:
2025-01-02's same-day-expiry contract was already lot size 75, while
2025-01-30's (a LATER date) was still 25. A simple date-range table
CANNOT represent this correctly for a specific contract.

THE FIX: src/lot_size.py's get_lot_size_for_contract(trade_date,
expiry_date) reads NewBrdLotQty directly from that date's own bhavcopy
for the specific contract -- authoritative. Falls back to
config/lot_size_history.csv (a clean date-range table, known-approximate
inside the ~2-3 month transition windows) ONLY when no bhavcopy is
available locally. ALWAYS returns (lot_size, source) as a tuple -- the
source tells you which path was used, so an approximation can never be
silently mistaken for ground truth. get_lot_size(trade_date) is the
same-day-expiry special case. Regression test in tests/test_lot_size.py
guards the exact bug this fixed (2025-01-30 returning 75 when the real
answer is 25).

CONSEQUENCE FOR REPORTING: because lot size is neither constant nor
knowable from a date alone without checking the actual contract, POINTS
is the primary, durable metric everywhere in this project from the lot-
size-audit onward. `pnl_points = (call_entry + put_entry) - (call_exit
+ put_exit)` never touches lot size and is exactly reproducible
regardless of any lot-size correction. Rupees are reported as a
secondary, explicitly-dated conversion using the real per-contract lot
size, never a flat assumption, from that point forward.

The original 136-trade baseline's rupee total (Rs 171,473.25, in
RESULTS.md) used a flat lot size of 65 for every trade -- overstated for
the 50- and 25-lot eras, understated for the 75-lot era. The corrected
figure (below) uses the actual per-trade lot size.

10. THE ONGOING TUESDAY (OR THURSDAY, PRE-REGIME) BLOTTER ROUTINE
================================================================================

src/paper_blotter.py runs ONCE per real NIFTY weekly expiry day, AFTER
market close, once NSE has published that day's bhavcopy. It downloads
that exact date only (no holiday rollback -- if the file isn't there,
that's the answer, not a reason to substitute another date), confirms it
really was a same-day-expiry day, and if so applies the pre-registered
rule exactly (reusing backtest_strangle.select_strikes() directly) and
appends one row to outputs/paper_blotter.csv, including a blank `notes`
column for manual annotation. It is idempotent -- a date already recorded
is skipped, and existing rows (including hand-written notes) are never
rewritten.

THIS NEVER PLACES, SIMULATES PLACING, OR CONNECTS TO ANYTHING THAT PLACES
A LIVE ORDER. It is a record of what the rule would have done, nothing
more.

Forward entries here must NEVER be merged with, or reported alongside as
one combined number with, the historical backtest (outputs/backtest_trades.csv
or outputs/backtest_trades_137.csv). A backtest already knows every
trade's outcome before analysis begins; forward paper trading doesn't.
Mixing them would launder one kind of evidence into looking like the
other. Any future summary of blotter performance should stand entirely
on its own, dated from whenever it actually starts accumulating real
entries.

Run it with: .venv/bin/python src/paper_blotter.py
(optionally --date YYYY-MM-DD to backfill a specific past expiry day;
defaults to today.)

11. REMAINING WORK -- NOT STARTED: THE PLEDGED-COLLATERAL STUDY
================================================================================

This has NOT been started. My own description of it, recorded here as
given so a future session has the actual framing rather than a
paraphrase that drifts from what I meant:

THE IDEA: I hold long-term equity positions I don't intend to sell. NSE
brokers let you PLEDGE existing shareholdings as collateral margin for
F&O positions, instead of posting cash margin. The question is whether
this strategy could be run as an OVERLAY on top of my existing holdings,
using pledged shares as the margin source rather than fresh cash -- a
"return stacking" framing: the shares keep doing whatever they do
(dividends, long-term appreciation, no change in my holding intent), and
the strangle premium is an additional return stream stacked on top,
funded by collateral that would otherwise just sit there.

THE WRONG-WAY-RISK CONCERN (my own flag, needs to be taken seriously, not
waved away): a short strangle loses the most on a big adverse index move.
If my pledged collateral is broad-market equity exposure, a bad day for
the index is very plausibly ALSO a bad day for my pledged shares' value
-- margin calls or forced deleveraging on the options side could coincide
with the pledged collateral itself being worth less, at the worst
possible time. This is the textbook definition of wrong-way risk and
needs to be modeled explicitly, not assumed away because it "sounds
diversified."

THE SEBI CASH-MARGIN REQUIREMENT (needs verification from PRIMARY
sources, not assumed): my understanding is SEBI requires some minimum
percentage of margin to be in CASH (or cash-equivalent) even when using
pledged securities for the rest -- meaning this can't be 100% collateral-
funded regardless of how much stock is pledged. The exact percentage,
which segment(s) it applies to, and whether it's changed recently all
need to be checked against SEBI's own circulars or NSE's own margin
framework documentation, the same standard this project has held itself
to everywhere else (see the lot-size and holiday sections above -- verify
against the primary source, don't trust a secondary summary blindly).

MY OWN PROPOSAL FOR DAMAGE CONTROL (explicitly flagged by me as something
that NEEDS TESTING, NOT ASSUMING TO WORK): on a crash day, buy MORE of
the pledged shares -- the idea being that a large adverse move that hurts
the strangle might also make the long-term holding cheaper to add to,
partially offsetting the margin-call risk with a lower average cost basis
on the equity side. This is a hypothesis about a specific mechanism, not
a settled plan. Before treating it as a mitigation, it needs to be
modeled against actual historical crash days (this project already has
several real ones: 2024-06-04 is the obvious first test case, and the
2020 COVID period from the regime-extrapolation estimate, caveated
appropriately since that period has no real option data) to see whether
buying more shares on the worst days actually would have offset enough
of the margin pressure to matter, or whether it's a comforting idea that
doesn't hold up numerically.

WHAT A FIRST PASS AT THIS STUDY SHOULD PROBABLY LOOK LIKE (my own rough
sketch, not a commitment to this exact structure -- reconsider if a
better approach is obvious once you're in it):
  1. Pre-register the question and the metric before computing anything,
     same as every other study in this project.
  2. Verify the actual SEBI cash-margin-percentage requirement from a
     primary source (SEBI circular or NSE margin framework doc), cited,
     the same way the lot-size circulars were verified in this project
     (the Diwali holiday explanation, by contrast, was NOT verified
     against a primary source -- see "Open questions -- claims to
     verify" below -- do not repeat that gap here).
  3. Model margin requirement per trade under a pledged-collateral
     assumption (using the margin methodology already built in
     outputs/margin_return_analysis.csv as a starting point, not from
     scratch).
  4. Explicitly model the wrong-way-risk correlation -- does the pledged
     collateral's value actually move against the strangle on the worst
     days in this project's own data? Test this, don't assume a
     correlation coefficient.
  5. Test the "buy more on crash days" proposal against real historical
     crash days in this project's data, reporting whether it would have
     helped and by how much, not whether it sounds reasonable.
  6. Report honestly if the answer is "this doesn't work" -- that would
     be as valid and useful a finding as any other result in this
     project's history (see: the strike-distance grid, the pre-holiday
     hypothesis, four of five every-day predictions -- this project's
     track record is full of hypotheses that didn't hold up, and that's
     fine).

No file for this exists yet. Start with a pre-registration file in
config/, following the exact pattern of config/strike_distance_experiment.json
or config/everyday_experiment.json, and a corresponding journal entry,
before writing any analysis code.
